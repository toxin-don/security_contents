## 経緯

久しぶりにPlaywrightを触っています。以前使っていたのは生成AIが普及する前の段階で、戻ってきてみると一番変わっていたのは「生成AIにテストを書かせ、メンテまでさせられる」ようになったことでした。Playwright本体にも[Test Agents](https://playwright.dev/docs/test-agents)という公式機能（v1.56〜）が入っていて、`npx playwright init-agents --loop=claude` を叩くとClaude Code用のエージェント定義（🎭Planner / Generator / Healer）が生成されます。そして `--loop=codex` とすればCodex用の定義も出てくる。

つまり、**同じテスト計画（spec）を入力に、Claude CodeとCodexへ同条件でテストコードを生成させられる**わけです。これは比較したくなります。ついでに、コードを生成せずAIがMCP経由でブラウザを直接操作してテストを実行する「コードレス実行」方式とも比べました。

結論を先に書くと、**生成物の品質はほぼ同着でした。差はコードではなくプロセスに出ました。**

## 実験の題材と統制条件

被検体は自作の学習用タスクボードアプリです。ランダム遅延（200〜1200ms）、リクエストごとにランダムな一覧順、3秒で消えるトースト、5秒ポーリングの通知バッジなど、**フレーキーテストの原因になる仕掛けを意図的に10種類仕込んであります**。環境変数でランダム性を無効化した決定的モードにも切り替えられます。

比較実験は言った者勝ちになりやすいので、実行前にプロトコルを固定してコミットしました。

- **共有インプット**: Plannerが生成したテスト計画（Markdown、3シナリオ）を両者共通の入力とし、**Generator工程だけ**を比較する（探索能力の差と生成能力の差を混ぜない）
- **公式loop定義を無改変使用**: `init-agents` の生成物をそれぞれのネイティブ環境でそのまま使う
- **one-shot**: 指示文言は事前固定。介入したら回数と内容を記録する
- **評価は6軸**: ロケータ品質（grep機械集計）/ アサーション品質 / フレーキー度（chaosモードで10回×3ラウンド）/ lint違反数（autofix前）/ テスト独立性 / 保守性（目視・主観と明記）

バージョン: Playwright 1.61.1 / Claude Code CLI 2.1.220（エージェント定義に固定されたSonnetで生成） / codex-cli 0.145.0（gpt-5.6-sol、reasoning effort low ※手元のデフォルト設定のまま）。

計画の入力には、テスト戦略の言語化（E2Eで担保する領域・価値ベースのassert・代表2本に絞る）と観点セットを事前に用意してあります。これが後で効いてきます。

共有したテスト計画の抜粋（シナリオ1）:

```markdown
#### 1.1. タスクを追加して完了にするとリロード後も反映されている
**Steps:**
  1. 前提: ログイン済みで /index.html を開く
    - expect: 見出し「タスク一覧」が表示される（陽性ランドマーク）
  2. Date.now() を含むユニークなタイトルを入力して「追加」をクリック
    - expect: role=status の通知に「「〈タイトル〉」を追加しました」
    - expect: 一覧内にそのタイトルを含む listitem が表示される
  3. チェックボックスをクリックして完了状態にする
    - expect: checked 状態になる
  4. ページをリロードする
    - expect: 自分のタイトルの listitem が残り、checked のままである（サーバ保存の証拠）
```

## 実験①: 生成されたコードはほぼ同着だった

6軸の結果です。

| 軸 | Claude Code (Sonnet) | Codex (gpt-5.6-sol low) |
|---|---|---|
| ロケータ | getByRole **16** / CSS・XPath・nth **0** | getByRole **22** / 同 **0** |
| アサーション | `await expect` 17、web-first 100% | 同17、+spec外の`statusText`検証1件 |
| lint違反（autofix前） | **0** | **0** |
| フレーキー度（chaos 10回×3） | **30/30 pass** | **28/30**（別途単独20回は20/20） |
| テスト独立性（並列・単体） | green | green |
| 行数 | 95 | 81 |

一番驚いたのはlintです。このリポジトリでは `eslint-plugin-playwright` を `--max-warnings 0` で運用していますが、**両者とも素の生成コードが無修正で通りました**。ロケータもCSSセレクタ・XPath・位置指定（nth/first）がゼロで、全てアクセシブル名ベース。「AIが書くテストは壊れやすいセレクタだらけになる」という事前の予想は、この条件では外れました。

コードの差分は作法レベルです。例えばリロード後の検証部分。

Claude Code（ロケータ変数を再利用。Locatorが遅延解決されることを分かっている書き方）:

```ts
await page.reload();
await expect(page.getByRole('heading', { name: 'タスク一覧' })).toBeVisible();
await expect(taskItem).toBeVisible();        // リロード前に定義した変数をそのまま使う
await expect(taskCheckbox).toBeChecked();
```

Codex（リロード後に改めて宣言。冗長だが明示的）:

```ts
await page.reload();
await expect(page.getByRole('heading', { name: 'タスク一覧' })).toBeVisible();
const persistedTask = page.getByRole('list', { name: 'タスク一覧' })
  .getByRole('listitem').filter({ hasText: title });
await expect(persistedTask).toBeVisible();
await expect(persistedTask.getByRole('checkbox', { name: `「${title}」を完了にする` })).toBeChecked();
```

どちらが良いかはチームの規約の問題で、品質の差とは言えません。フレーキー度でCodex側に28/30という数字がありますが、失敗した2件は単独で20回再実行しても再現せず、原因は特定できていません（後述の「正直な記録」参照）。アルプ社の言う「安定度」（ノーミス確率）で表すと、Claude 100% / Codex 93.3%（単独再実行では100%）です。

### 差はプロセスに出た

生成物が同着だった一方、**ヘッドレスで動かすまでの摩擦**にははっきり差がありました。

Claude Code側は `init-agents` 後、初回で動きました。Codex側は3回の介入が必要でした。

1. 認証エラー（対話セッションとrefresh tokenが競合）
2. MCPのブラウザ操作ツールが全て `user cancelled MCP tool call` で拒否される（`approval_policy="never"` でも解決せず）
3. `--dangerously-bypass-approvals-and-sandbox` でようやく通る

ただし、介入2の場面でCodexが見せた挙動は特筆ものでした。ブラウザ操作ができない状態で、こう報告して**生成0件のまま降りた**のです。

> 指示に反してテストを捏造・手書きすることは避けたため、生成ファイルは0件です。Playwright MCP の操作許可を有効にしてから、再実行を依頼してください。

「実ブラウザで確認できないものは書かない」。生成AIテストの信頼性という観点で、これは高く評価したい性質です。想像でコードをでっち上げられるより、止まってくれる方がずっといい。

## 実験②: コード実行 vs MCP直接駆動は600〜1000倍差

もう一つの比較は実行方式です。生成したテストコードを回すのではなく、AIがPlaywright MCP経由でブラウザを直接操作してシナリオを実行する方式（コードレス）を、同じシナリオ1で3回試しました。駆動役はヘッドレスのClaude Code（Sonnet）+ 公式の `playwright run-test-mcp-server` です。

| 方式 | 所要時間 | LLMコスト |
|---|---|---|
| 生成済みコードの実行 | **0.24〜0.26秒/回** | 実行時ゼロ |
| MCP直接駆動 run1 | 248秒 | $1.43（45ターン） |
| MCP直接駆動 run2 | 155秒 | $0.80（29ターン） |
| MCP直接駆動 run3 | 132秒 | $0.74（27ターン） |

3回ともPASSしましたが、面白かったのはrun1です。このアプリのトーストは3秒で自動消滅する仕掛けなのですが、run1のAIは検証ツールを呼んだ時点でトーストが消えており、「クリック直後のスナップショットに通知の記録があった」ことを根拠にPASS判定を出しました。**人間のテスターのような柔軟なリカバリであると同時に、実行のたびに検証の根拠が変わりうる**ということでもあります。コード化されたassertの決定性との本質的な違いがここに出ました。

この2方式の比較は、[FindyのPlaywrightイベント](https://www.youtube.com/watch?v=pUPPcNN9O8M)で大湯氏が発表されていた「コード生成（検証1）とMCP直接駆動（検証2）の使い分け」の小規模追試です。手元の数字でも同じ結論になりました。**毎デプロイ回すリグレッションは生成コード、コード資産がない新シナリオの初回確認はMCP直接**、という役割分担です。

## 考察: なぜ品質が同着になったのか

種明かしをすると、この比較実験は基礎から積み上げてきた学習リポジトリの最終段で、生成の入力には次が揃っていました。

- テスト戦略の言語化（E2Eの担保領域・CUJ代表2本・価値ベースassert）
- E2E向けにフィルタしたテスト観点セット
- 認証済み状態を確立するseedテストと、`storageState`・データ独立・待機規律が入った既存テスト群
- `eslint-plugin-playwright` による規律の機械化

つまり両AIは「良いテストの書き方が実物として揃ったリポジトリ」の中で生成しています。CADDiさんの実験記事に[「仕様書の書き方次第でAI生成テストの品質が2〜3倍変わる」](https://caddi.tech/2026/05/26/173903)という知見がありますが、今回の結果はその追試になっていると思います。**どのAIが賢いかより、何を読ませるかが生成の質を決める。しかもそれはベンダーを跨いで成立する** — これが今回の実験で一番持ち帰りたい結論です。

コストの目安も置いておきます。Codexの3シナリオ生成は277秒・33,114トークンでした。MCP直接駆動は1シナリオ1回あたり$0.7〜1.4。1日10デプロイ×数シナリオをコードレスで回すと月数百ドル規模になる計算で、「生成は1回、実行はタダ」のコード方式との差は運用頻度が上がるほど開きます。

## 正直な記録（うまくいかなかったこと）

- Codex側のフレーキー2件（28/30）は**エラー詳細の取り逃し**をやらかしました。ログをtailで切り詰めていたせいです。単独再実行20回では再現せず、原因未特定のまま記録しています
- Claude側の生成時間とトークン数は**計測し忘れました**。比較実験を後付けで設計したツケです
- SonnetとGPT-5.6-sol（low）という**モデルも推論設定も揃っていない比較**であり、優劣の結論には使えません。「同じ入力なら両者とも規律に乗る」という観察までが今回の射程です

## まとめ

- 同一のテスト計画・同一のリポジトリを入力にすると、Claude CodeとCodexの生成テストは**ロケータ純度100%・lint 0違反で同着**だった
- 差は生成物ではなく**プロセス**（ヘッドレス化の摩擦、コードの作法）に出た。Codexの「実行できなければ捏造しない」は好印象
- 実行方式は**コード0.25秒 vs MCP直接150〜250秒・$1前後**。定常はコード、初回探索はMCP直接という使い分けが数字で裏付けられた
- 生成AIにE2Eを書かせる前にやるべきは、AI選定ではなく**入力の整備**（戦略の言語化・観点の絞り込み・規律の機械化・良い実例）
