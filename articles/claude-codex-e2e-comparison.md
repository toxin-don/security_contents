## 経緯

久しぶりにPlaywrightを触っています。以前使っていたのは生成AIが普及する前で、復帰して驚いたのが公式のAIエージェント機能[Test Agents](https://playwright.dev/docs/test-agents)（v1.56〜）でした。セットアップの `init-agents` は `--loop=claude` と `--loop=codex` の両方に対応しています。つまり、同じテスト計画から2つのAIへ同条件でテストを生成させて比べられます。

やってみた結果、生成物の品質はほぼ同着でした。差はコードではなくプロセスに出ました。

## 実験の条件

被検体は自作のタスクボードアプリです。ランダム遅延やランダムな一覧順など、テストが不安定になる仕掛けを意図的に10種類仕込んであります。

言った者勝ちにならないよう、実行前に条件を固定してコミットしました。

- 共有インプット: 🎭Plannerが生成したテスト計画（3シナリオ）。比較するのはGenerator工程だけ
- 公式のエージェント定義を無改変で使用。指示文も事前固定のone-shot
- 評価6軸: ロケータ品質・アサーション品質・フレーキー度・lint違反数・テスト独立性・保守性
- 版: Playwright 1.61.1 / Claude Code CLI 2.1.220（Sonnet固定）
- Codex側: codex-cli 0.145.0（gpt-5.6-sol、reasoning effort low）

生成の入力には、テスト戦略の言語化（E2Eで担保する領域・価値ベースのassert・代表2本に絞る）と観点セットを事前に用意してあります。これが後で効きます。

## 結果1: 生成コードはほぼ同着

| 軸 | Claude Code | Codex |
|---|---|---|
| ロケータ | getByRole 16 / CSS・XPath・nth 0 | getByRole 22 / 同0 |
| lint違反（autofix前） | **0** | **0** |
| フレーキー度（chaos 30回） | 30/30 | 28/30 ※単独20回は全通過 |
| 行数 | 95 | 81 |

一番の驚きはlintです。`eslint-plugin-playwright` を警告ゼロで運用しているリポジトリで、両者とも素の生成コードが無修正で通りました。ロケータは全てアクセシブル名ベースで、壊れやすいセレクタはゼロです。

コードの差は作法レベルでした。リロード後の検証で、Claudeはロケータ変数を再利用し、Codexは宣言し直します。

```ts
// Claude: リロード前の変数をそのまま使う（Locatorは使う瞬間に再解決される）
await expect(taskCheckbox).toBeChecked();
```

```ts
// Codex: リロード後に宣言し直す（冗長だが明示的）
const persistedTask = page
  .getByRole('list', { name: 'タスク一覧' })
  .getByRole('listitem').filter({ hasText: title });
await expect(persistedTask.getByRole('checkbox', { name: `「${title}」を完了にする` })).toBeChecked();
```

一方、プロセスには差が出ました。Claude側は初回で動作し、Codex側はヘッドレス実行までに3回の介入（認証の競合、MCPツール承認まわりで2回）が必要でした。ただしCodexは、ブラウザを操作できない状態でこう報告し、生成0件で止まりました。

> 指示に反してテストを捏造・手書きすることは避けたため、生成ファイルは0件です。

実行できないなら書かない。生成AIテストの信頼性として、この性質は評価できます。

## 結果2: コード実行とAI直接実行は600倍差

生成したコードを実行する方式と、AIがMCP経由でブラウザを直接操作してシナリオを実行する方式（コードレス）を、同じシナリオで比較しました。駆動役はヘッドレスのClaude Code（Sonnet）+ 公式 `run-test-mcp-server` です。

| 方式 | 時間 | LLMコスト |
|---|---|---|
| 生成コードの実行 | 0.25秒/回 | 実行時ゼロ |
| AI直接実行（3回） | 132〜248秒 | $0.74〜1.43/回 |

3回とも通りました。ただ1回目のAIは「3秒で自動的に消えるトースト」に遭遇し、クリック直後のスナップショット記録を根拠にして判定しました。柔軟である一方、実行のたびに検証の根拠が変わるということです。コード化されたassertの決定性とは別物でした。

毎回のリグレッションは生成コード、コード資産のない新シナリオの初回確認はAI直接。この使い分け（着想元: [FindyのイベントでのTOWN大湯氏の発表](https://www.youtube.com/watch?v=pUPPcNN9O8M)）が、手元の数字でも裏付けられました。

## 考察: なぜ同着になったのか

両AIは「良いテストの書き方が実物として揃ったリポジトリ」の中で生成しています。戦略の言語化、観点の絞り込み、lintによる規律の機械化、認証やデータ独立の実例。この入力が同じなら、どちらのAIも同じ規律に乗りました。[CADDiさんの実験記事](https://caddi.tech/2026/05/26/173903)に「仕様書の書き方でAI生成テストの品質が2〜3倍変わる」という知見がありますが、今回はその追試になりました。

**どのAIが賢いかより、何を読ませるか。**

## 正直な記録

- Codexの失敗2件はログの取り方が悪く、エラー詳細を取り逃した。単独再実行20回では未再現
- Claude側の生成時間とトークン数は計測漏れ
- SonnetとGPT-5.6-sol（low）はモデルと推論設定が不揃い。優劣の結論には使えない

## まとめ

- 同じ計画・同じリポジトリなら、Claude CodeとCodexの生成テストはロケータ純度100%・lint 0違反で同着
- 差はプロセス。Codexの「実行できなければ書かない」は好印象
- 実行方式は0.25秒 vs 132〜248秒・$1前後。定常はコード、初回探索はAI直接
- AI選定の前に入力の整備。戦略の言語化と規律の機械化が生成の質を決める
